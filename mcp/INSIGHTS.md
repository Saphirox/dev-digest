## What Doesn't Work

- 2026-09-26 · Moving `client.ts`'s `parseArray`/`parseObject` into the new `lib/` ring (item 4, polish pass) was considered and rejected: both throw `MalformedResponse` (`platform/errors.ts`), and the `lib` kind's architecture rule is "imports nothing internal, only `zod`" — making them lib-safe would mean returning `null`/`undefined` on a parse failure instead of throwing, pushing the `if (!parsed) throw new MalformedResponse(endpoint)` into all 9 repository call sites across 4 files for no architectural gain. Only the genuinely dependency-free helper (`truncate`) moved to `lib/text.ts`; `parseArray`/`parseObject` stayed in `adapters/devdigest-api/client.ts`.
- 2026-09-27 · Turning a documented "stub" module into a real one (the 2026-09-27 `repo-intel` → `blast` swap) does not retire every prose mention of "stub" in one pass: the module-list line (`mcp/AGENTS.md`'s `<agents|reviews|conventions|repo-intel>`) got fixed in the original build, but a separate paragraph two screens down still called `blast/` "a `tools.ts`-only stub … no service/repository yet" and referenced the by-then-deleted `blastRadiusStubMessage()`, plus the sibling reference doc (`.claude/skills/onion-architecture/references/mcp-package.md`) had its own independent "a stub for now" line — both survived until two independent reviewers flagged them separately. `grep -rn "stub"` across every doc that describes the module (not just the one you edited) is the cheap check; a single doc can name a module as a stub in more than one place.

## Codebase Patterns

- 2026-09-26 · `mcp/src` mirrors `server/src`'s module layout (`modules/<f>/{ports,repository,service,helpers,constants,tools,render}.ts`, `modules/_shared/`, `platform/{config,container,errors,log}.ts`, `app.ts`+`server.ts`), per `.claude/skills/onion-architecture/references/mcp-package.md`. No central `ports.ts`/`domain/`/`usecases/` anymore — each module owns only the fields it reads (`AgentRef` in `modules/_shared/ports.ts` is `{id,name}`, not the full `AgentRecord`, because `Resolver.resolveAgent`/`ReviewsService.runAgentOnPr` only ever read `.id`/`.name`).
- 2026-09-26 · Supersedes the same-day "`platform/container.ts` … is the only file that constructs concrete repositories/services" entry below it: WRONG once compared against `server/`'s actual pattern — server's `routes.ts` builds its own service from `container.db` (`modules/pulls/routes.ts:26-30`), and `platform/container.ts` only holds cross-cutting infra (config, db, shared adapters). The first restructure pass copied server's FOLDER names but kept the container building every module's service, which is closer to a service-locator than server's real DI shape. Fixed (server-parity pass): `container.ts` now exposes only `client`/`resolver`/`waitMs`/`pollMs`; each module's `tools.ts` builds `new <F>Service({ store: new <F>ApiRepository(container.client), resolver: container.resolver })` itself. Lesson: when a plan/skill doc says "mirrors server/", diff the actual wiring against the named server file, not just the folder names — `architecture-reviewer` caught this the pass after it shipped.
- 2026-09-26 · `test/tools.test.ts`'s container-level test double is the HTTP client (`FakeApiClient` implementing `get`/`post`, injected via a plain object satisfying `AppContainer`), not per-module fake stores — once `tools.ts` builds its own real repository+service from `container.client`, faking anything above the HTTP boundary would mean NOT exercising the real repository/service wiring the restructure exists to prove. One client double routes by path string for every module's endpoint (`/repos`, `/agents`, `/repos/:id/pulls`, `/repos/:id/conventions`, `/pulls/:id/runs(|/active|/review|/reviews)`) — simpler than it sounds because `run_agent_on_pr`'s only test scenario is "never reaches done", so no per-call-count scripting is needed at the HTTP layer (unlike `ScriptedReviewsStore`, still used by `reviews-service.test.ts`, which tests the service directly and DOES need per-call scripts).
- 2026-09-26 · Supersedes the entry above for the two `InMemoryTransport` test files: `test/tools.test.ts`/`test/tools-end-to-end.test.ts` now build `makeContainer()` with `new Container({ apiUrl: 'http://fake', waitMs: 30 }, { client: fake, pollMs: 10 })` (a real `Container`) instead of a hand-assembled `AppContainer` object literal — the object literal was a plausible-looking fake that skipped the container's own `resolver`/`pollMs` wiring entirely; the polish pass (item 3) caught that `ContainerOverrides.pollMs` was declared but never assigned in the constructor (`platform/container.ts`), which no test had caught because no test constructed a real `Container` with that override before.
- 2026-09-26 · A new `lib` ring resolves a class of "N near-identical copies, each justified by 'no ring all four could jointly import from'" duplication (here: 4 copies of `truncate`, see the superseded Tool & Library Notes-adjacent comments each copy used to carry) — add a `lib/` folder that imports nothing internal and only third-party packages (`zod` here), let every other kind import IT, and the duplication justification disappears without widening any existing kind's own allowlist. Precedent: `server/src/lib/diff-lines.ts`. In `mcp/test/architecture.test.ts` this means one more `Kind` value with an internal-imports list of `[]` and an external-imports predicate, plus adding `'lib'` to the *importer* side of `helpers`/`render`/`adapter`/`repository`/every `shared-*` kind's `ALLOWED_INTERNAL` entry.
- 2026-09-27 · A module's `render.ts` can never import `_shared/messages.ts` — `test/architecture.test.ts`'s `ALLOWED_INTERNAL['render']` is `['helpers', 'ports', 'constants', 'lib']` only, no `shared-messages` entry. When a render function needs catalogue prose (e.g. a "no callers" line, a degraded-reason line), thread it in as a plain string PARAMETER from `tools.ts` instead (`blast/render.ts`'s `renderBlastRadius(pr, blast, noCallersText)`; `tools.ts` calls `messages.ts`'s `noCallersMessage()`/`degradedReasonMessage()` and passes/prepends the result) — the same place `reviews/tools.ts` already composes `render.ts` line lists with `messages.ts`'s non-error texts (`getFindingsRunningMessage()`, `fullDetailHint()`), just not yet written down as a rule. Relatedly, `_shared/messages.ts` itself (`shared-messages` kind) cannot import a module's `ports.ts` either (`ALLOWED_INTERNAL['shared-messages']` has no `ports` entry) — a reason/status union a module defines (e.g. `blast/ports.ts`'s `BlastDegradedReason`) has to be re-typed as a local literal union in `messages.ts` rather than imported.

## Tool & Library Notes

- 2026-09-26 · zod 4 → JSON Schema (what `tools/list` ships) is far costlier than the zod source suggests: every `.int()` emits an explicit safe-integer `minimum`/`maximum`, `.uuid()` emits a ~230-char regex, and repeated `z.enum()` literals are NOT deduped via `$ref`. The first full draft measured 7,601 chars vs the 6,000-char budget in `test/tools.test.ts`; it fit (5,923) only after dropping `.int()`/`.uuid()` on inputs and using plain `z.string()` for server-composed output fields (now `modules/_shared/schemas.ts` + each module's `tools.ts`). Before adding a tool or field, run `npm test` and read the printed `tools/list serialized size` — budget headroom is ~50 chars post-restructure (5,950/6,000).
- 2026-09-26 · MCP TS SDK 2.0.0: the tool handler's 2nd arg is `ctx` (`ctx.mcpReq.signal`, `ctx.mcpReq._meta?.progressToken`, `ctx.mcpReq.notify(...)`), not v1's `extra`; schemas must be `z.object(...)` (raw shapes are deprecated). Pin `@modelcontextprotocol/server`/`client` to exactly `2.0.0` — `^2.0.0` pulls 2.1.0 and a second `@modelcontextprotocol/core`.
- 2026-09-26 · A class with any `private`/`readonly` constructor param (e.g. `DevDigestApiClient`, `AgentsApiRepository`) is nominally typed, not structural — a plain fake object literal (`{get: vi.fn(), post: vi.fn()}`) does not satisfy its type even with matching public methods. `test/repositories.test.ts` uses a small `FakeClient` class plus `as unknown as DevDigestApiClient` at the call site rather than fighting the type system.
- 2026-09-26 · An abstract base class gives a real TS-checked exhaustive switch over a hand-rolled error hierarchy: `platform/errors.ts`'s `McpError` declares `abstract readonly code: string`, each subclass overrides it with a literal (`readonly code = 'ApiUnreachable' as const`), and `DomainError` is the union of the 11 subclasses. `messages.ts`'s `toToolResult` casts the caught `McpError` to `DomainError` and switches on `.code`; the `default` branch assigns the switched value to a `const _exhaustive: never` — adding a 12th subclass without a matching `case` fails `tsc`, not just a runtime fallback. Also frees every subclass from manually setting `this.name = 'X'`: the base constructor does `this.name = this.constructor.name`, which resolves to the actual subclass name even when only called via `super()`.
- 2026-09-26 · A hand-rolled import scanner built on `ts.isCallExpression(node) && node.expression.kind === ts.SyntaxKind.ImportKeyword && ts.isStringLiteral(node.arguments[0])` (the original `test/architecture.test.ts`) misses two real import shapes, both provable in under a minute with a temporary mutant: (1) `` import(`literal/path.js`) `` — a template literal with no `${}` is a `NoSubstitutionTemplateLiteral`, not a `StringLiteral`; fix is `ts.isStringLiteralLike(node.arguments[0])`, which covers both. (2) `import('literal/path.js').SomeType` in TYPE position (no `import` keyword call at all) is a distinct AST node, `ts.ImportTypeNode`, with `node.argument` a `LiteralTypeNode` wrapping the string — needs its own `ts.isImportTypeNode(node)` branch. Neither gap raised a false negative in this package's own source (nothing used either shape), so it stayed invisible until deliberately probed with mutants — the same "probe with a mutant, not just a read" method as the root INSIGHTS "keyword matcher" entry, applied to static-analysis tooling instead of a runtime heuristic.
- 2026-09-26 · No `@vitest/coverage-v8` (or any coverage provider) is installed: `./node_modules/.bin/vitest run --coverage` fails immediately with `MISSING DEPENDENCY '@vitest/coverage-v8'`. Since installing one is out of bounds for a test-only task, gaps here have to be found by reading `src/` against the existing `test/` files, not measured — budget time for that read instead of assuming `--coverage` will work.
- 2026-09-26 · Detecting "is this import specifier type-only" with the TS compiler needs FOUR branches, not one flag: (1) `ts.ImportDeclaration.importClause.isTypeOnly` for a whole `import type {...} from '...'`; (2) each `ts.ImportSpecifier`'s OWN `.isTypeOnly` for an inline `import { type A, B } from '...'` — a declaration can mix type and value specifiers, so "some elements type-only" isn't "the whole import is type-only" (a default import or a namespace import (`import * as X`) is always a value, overriding any per-element flag); (3) the mirror image on `ts.ExportDeclaration` (`.isTypeOnly` + each `ts.ExportSpecifier.isTypeOnly`) for `export {...} from '...'`; (4) a type-position `ts.ImportTypeNode` (`import('...').Foo`) is unconditionally type-only by construction — it can't appear anywhere a value is expected. `test/architecture.test.ts`'s `importDeclarationIsTypeOnly`/`exportDeclarationIsTypeOnly` helpers encode this; verified with a mutant (a value import + `new Container(...)` call in `agents/tools.ts`) that both the new type-only-container check and the existing constructor check independently caught, then reverted.
- 2026-09-26 · `@modelcontextprotocol/client`'s `StdioClientTransport` (`node_modules/@modelcontextprotocol/client/dist/stdio.mjs`) spawns the child itself and only exposes `.stderr`/`.pid` publicly, but its `_process` (`ChildProcess`) field is only `private` in the `.d.ts` — at runtime (JS) `(transport as any)._process.stdout` is a real, readable stream. This lets a smoke test use the SDK's own correct protocol handshake (version negotiation, `initialized` notification via `Client.connect()`) while independently asserting on the raw stdout bytes (`test/server-stdio.test.ts`), instead of hand-rolling the wire protocol just to check "is every line valid JSON-RPC".
- 2026-09-27 · Supersedes 2026-09-26 "budget headroom is ~50 chars post-restructure (5,950/6,000)": turning `get_blast_radius` from a stub into a real, text-only (no `outputSchema`) tool moved `tools/list` to 5,952/6,000 — only 48 chars of headroom left, even with no output schema at all for the new tool. The input schema alone (`{repo, pr}`, reused from `_shared/schemas.ts`) and the `description` (~110 chars) were nearly free; almost the whole ~2-char net growth came from the tool's name+annotations entry in the list. Any next tool/field addition should budget for near-zero headroom and re-measure immediately.

## Recurring Errors & Fixes

- 2026-09-27 · `"get_blast_radius is not implemented yet. Use get_findings for review results."` from a live `mcp__devdigest__get_blast_radius` call, even after the stub had been replaced with a real tool on disk → the running MCP server is a stdio subprocess Claude Code spawns once at session start (via `.mcp.json`); unlike a Next.js dev server, it has no file-watcher/hot-reload, so it keeps serving the tool definitions/behavior from whenever the session's MCP connection was established. Verified: the server's own HTTP route for the same PR returned real data via `curl` while the MCP tool still returned the stub text in the same session. Fix: restart the session (or reconnect its MCP connection) before trusting a live tool call to reflect a code change made mid-session — the package's own test suite is the reliable signal in the meantime.

- 2026-09-27 · Follow-up to the stale-stub entry above: `/mcp` → reconnect `devdigest` is enough — no full session restart needed. After the reconnect, `get_blast_radius` returned real data (`Saphirox/dev-digest#6`: 6 symbols, 11 callers, 32 endpoints), yet the tool description Claude Code showed was still the old "Not implemented yet — placeholder …" text, which no longer appears anywhere in `mcp/src/modules/blast/tools.ts`. Judge whether the MCP server is current by what a call returns, not by the tool description.

## Open Questions

- 2026-09-26 · `get_findings`' `running_agents` is filled with run ids, not agent names: `GET /pulls/:id/runs/active` returns only `{run_id,status,error}` (`src/usecases/get-findings.ts`). Rename the field or join agent names via `GET /pulls/:id/runs` — undecided.
- 2026-09-26 · Supersedes 2026-09-26 "`get_findings`' `running_agents` is filled with run ids": resolved — the field is renamed `running_run_ids` (`modules/reviews/service.ts`'s `GetFindingsResult`), documented in `mcp/AGENTS.md`.
- 2026-09-26 · `client.ts`'s `fetchJson` (`src/adapters/devdigest-api/client.ts:39-64`) wraps only `await fetch(...)` in its try/catch; the success-path `return res.json()` is unguarded, so a malformed 200 body rejects with a raw `SyntaxError` instead of an `ApiUnreachable`/`ApiFailure` — verified failing in `test/client.test.ts`'s "non-JSON success body" describe block. Not fixed here (test-writer scope); the fix is likely wrapping that final `res.json()` in the same try/catch and mapping a parse failure to a new or existing typed error.
- 2026-09-26 · Resolved: the success-path `res.json()` in `fetchJson` is now wrapped in its own try/catch; a parse failure throws `ApiFailure(res.status, ...)` with a message carrying the request's method + path (e.g. `Malformed JSON body from GET /agents`), not `MalformedResponse` — `test/client.test.ts`'s repro only imports/asserts `ApiUnreachable`/`ApiFailure` (no `MalformedResponse` import at all), so reusing `MalformedResponse` here would fail that (unweakened) test. `MalformedResponse` stays reserved for a *repository's* schema `safeParse` failure (`parseArray`/`parseObject` in this same file), a different failure mode (200 + valid JSON, wrong shape) from "200 + invalid JSON" here.
- 2026-09-26 · Supersedes the entry above (polish pass): switched to `MalformedResponse(\`${method} ${path}\`)` after all — a 2xx status with an unparseable body IS a shape problem (closer to a repository's `safeParse` failure than a transport failure), and rendering it through `ApiFailure` produced a misleading "DevDigest API error 200: ..." tool message. `test/client.test.ts`'s repro test now imports `MalformedResponse` and asserts `instanceof MalformedResponse` directly (`err.endpoint === 'GET /agents'`), not just the looser `ApiUnreachable || ApiFailure` check the previous fix used.
